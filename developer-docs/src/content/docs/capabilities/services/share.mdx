## 三个请求

内容主动发起的分享都是宿主作答的请求，各走一个方法：

| migo API | Android `ShareHandler` | C ABI `MIGO_HOST_SERVICE_SHARE` |
| --- | --- | --- |
| `migo.shareAppMessage(options)` | `shareAppMessage(ShareRequest, ShareSink)` | `SHARE_APP_MESSAGE` 0 |
| `migo.shareMessageToFriend(options)` | `shareMessageToFriend(FriendShareRequest, ShareSink)` | `SHARE_MESSAGE_TO_FRIEND` 1 |
| `migo.showShareImageMenu(options)` | `showShareImageMenu(ImageShareRequest, ShareSink)` | `SHOW_SHARE_IMAGE_MENU` 2 |

Android 通过 `GameSession#setShareHandler(ShareHandler)` 注册；C ABI 宿主在 `host_services` 里声明 `MIGO_HOST_SERVICE_SHARE`，
在 `on_host_service_call` 里按方法号作答。

请求就是内容传给这次调用的内容，原样：`migo.onShareAppMessage` 监听器回答的是菜单里的「转发」，与主动的
`shareAppMessage` 无关，不参与这次请求。内容没设置的选项不出现（Android 的请求对象里是空串）。

## 图片路径

每个请求至多指名一张图片——`shareAppMessage` / `shareMessageToFriend` 的 `imageUrl`、`showShareImageMenu` 的
`path`。宿主收到的是这张图在游戏沙箱里对应的**真实文件路径**（`/user`、`/tmp`、`/cache` 或代码包里的文件；相对路径按代码包根目录解析），
在请求结束前一直可读；它绝不是内容给的原始字符串，所以内容无法借此让宿主读到沙箱外的文件。沙箱外或不存在的路径在离开引擎前就失败。
只有 `shareAppMessage` 的 `imageUrl` 可以是 http(s) URL，原样交给宿主；另两个拒绝网络图片。

## 请求字段

`ShareRequest`（`SHARE_APP_MESSAGE`）：

| 字段 | 语义 |
| --- | --- |
| `title` | 分享标题；内容未设置时为空串 |
| `imageUrl` | http(s) URL 或真实文件路径；未设置时为空串 |
| `query` | 目标游戏收到的查询串，如 `a=1&b=2`，不带前导 `?` |
| `imageUrlId` | 平台图片 id；宿主不能按该平台解析时忽略 |
| `toCurrentGroup` | 从群工具栏打开时是否转发回该群；内容未设置时为 `true` |
| `path` | 独立分包路径；未设置时为空串 |

`FriendShareRequest`（`SHARE_MESSAGE_TO_FRIEND`）：

| 字段 | 语义 |
| --- | --- |
| `openId` | 好友的 openId，内容给的原样；不为空 |
| `title` / `imageUrl` / `imageUrlId` | 同上；`imageUrl` 只能是真实文件路径 |
| `query` | `migo.setMessageToFriendQuery()` 设的查询，好友进入时出现在 enter options 的 `query.query` |
| `shareMessageToFriendScene` | 同上的 `query.shareMessageToFriendScene`，0–50；未设置为 `null`（C ABI 里缺省） |

`ImageShareRequest`（`SHOW_SHARE_IMAGE_MENU`）：

| 字段 | 语义 |
| --- | --- |
| `path` | 真实文件路径；不为空 |
| `needShowEntrance` | 图片消息是否带进入游戏的入口 |
| `entrancePath` | 入口打开的路径；为空表示默认 |

## 怎么作答

每个请求通过 `ShareSink`（C ABI：`migo_session_complete_host_service_call`）恰好 settle 一次：

| 方法 | 语义 |
| --- | --- |
| `settleShared()` | 分享流程结束；不代表用户实际发送了消息 |
| `fail(int errCode, String errMsg)` | 失败，`errMsg` 原样交给内容 |

分享等的是玩家，玩家用多久就等多久，runtime 不设超时。调用从 runtime 宿主线程到达，不要在其中阻塞；`ShareSink` 可从任意线程调用，
首个 settle 生效、后续被忽略。

`shareMessageToFriend` 结束后，内容的 `migo.onShareMessageToFriend` 监听器会收到 `{success, errMsg}`——由这次请求的结算派生，
宿主不需要另发事件。

## 分享菜单

菜单（右上角的「转发」「分享到朋友圈」「收藏」）是宿主的。小游戏的分享项默认隐藏，内容用 `showShareMenu` 打开：

- 每次 `showShareMenu` / `hideShareMenu` / `updateShareMenu` 之后，宿主收到菜单的**完整状态**——Android
  `ShareHandler.onShareMenuChanged(ShareMenu)`，C ABI 命令 `SET_SHARE_MENU` 3（`{"menus", "withShareTicket", ...updateShareMenu 的字段}`）。
  「分享到朋友圈」只和「转发」一起出现。
- 玩家点了某项，宿主问游戏分享什么——Android `GameSession.requestMenuShare(menu, MenuShareCallback)`，C ABI 事件
  `EVENT_MENU_SHARE` 0（`{"menu", "replyId"}`，`menu` 为 `shareAppMessage` / `shareTimeline` / `addToFavorites`）。
- 内容对应的 `onShareAppMessage` / `onShareTimeline` / `onAddToFavorites` 监听器作答（最后一个返回对象的为准；`onShareAppMessage`
  返回值里的 `promise` 最多等 3 秒，以其 resolve 结果为准），答复恰好一次——`MenuShareCallback.onShareContent(MenuShareContent)`，
  C ABI 命令 `MENU_SHARE_REPLY` 4（`{"replyId", "menu", "content"}`）。没有监听者、或运行时先重启时，答复为 `null`，宿主按自己的默认
  （游戏名、图标）分享。答复里的图片同样是经沙箱解析的真实文件（会话期内可读）或 http(s) URL；不是游戏自己文件的图片被丢弃。

## 不实现会怎样

没有 handler（或 C ABI 宿主没声明 share 服务）时，三个请求都以 `<api>:fail not supported`、错误码 `-2` 失败。它们会 settle 而不是沉默：
内容常常等分享结束才继续，丢掉的请求就是一局暂停的游戏。

`migo.shareAppMessage()` 的成功只表示分享流程结束；与常见小游戏平台一样，内容不会知道用户是否真的发送了消息，凭它发奖励没有事实依据。
