`GameSession` owns the native session (`sessionId`) and bridges it to the Activity and views. It implements `Closeable` and must be closed explicitly.

## Minimal lifecycle

```java
// in the surfaceCreated callback
session = runtime.createSession(activity, surface, config, gameId);
session.startGame("game.js");        // game.js lives under session.getPaths().getCodeDir()

// Activity
@Override protected void onPause()  { if (session != null) session.pause();  }
@Override protected void onResume() { if (session != null) session.resume(); }
@Override protected void onDestroy(){
    if (session != null) { session.close(); session = null; }
}
```

After `close()`, methods guarded by `ensureNotDestroyed` throw `MigoException` (code `-2000 ERR_SESSION_DESTROYED`, extending `RuntimeException`); `pause()` and `resume()` are safe no-ops, and `dispatchTouchEvent` returns `false`. Until the session is closed, native memory, the JS context, and platform channels are not released.

## The three Surface callbacks

These correspond to the three `SurfaceHolder` callbacks:

```java
surfaceView.getHolder().addCallback(new SurfaceHolder.Callback() {
    public void surfaceCreated(SurfaceHolder h)  { /* createSession */ }
    public void surfaceChanged(SurfaceHolder h, int fmt, int w, int h) {
        session.updateSurface(h.getSurface(), w, h);
    }
    public void surfaceDestroyed(SurfaceHolder h) {
        session.onSurfaceDestroyed();       // the engine takes the surface-lost path; JS onHide fires here
    }
});
```

Forgetting `onSurfaceDestroyed` is the most common source of deadlocks: the engine does not know the Surface is gone, and GPU resources remain attached to the destroyed object.

## Touch and script channels

```java
surfaceView.setOnTouchListener((v, ev) -> session.dispatchTouchEvent(ev));

// host → JS
session.evaluateJavaScript("console.log('hello from host')");

// JS → host: migo.sendToHost(type, payload) arrives here
session.setMessageHandler((type, payload) -> { /* JSON String, may be null */ });
```

`evaluateJavaScript` returns immediately; the script is queued asynchronously on the host thread. To receive a reply, pair `migo.sendToHost` with `MessageHandler`.

### Desktop form: mouse, cursor, pointer lock

On a device with a mouse (a docked phone, a Chromebook, desktop windowing), give the session the view the game is in:

```java
session.setInputView(surfaceView);
```

The session takes over that view's generic-motion and captured-pointer listeners: hovering, buttons and the wheel reach
content's `onMouseMove` / `onMouseDown` / `onMouseUp` / `onWheel` (CSS pixels, DOM button order; the touches Android
makes of mouse clicks still reach `onTouch*`, as on the platform's PC client), `migo.setCursor()` sets the view's
`PointerIcon`, and `requestPointerLock()` uses pointer capture, whose relative motion accumulates into positions so
`movementX/Y` keep coming. `MigoGameView` and `MigoGameActivity` do all of this themselves. A view of your own calls
`session.onPointerCaptureChanged(hasCapture)` from its `View.onPointerCaptureChange`; when forwarding events by hand,
use `session.dispatchGenericMotionEvent(ev)`. When the window moves between freeform/split screen and maximized
(Android 11+), content hears `onWindowStateChange`; an Android app cannot size its own window, so `setWindowSize` is not
supported.

### Physical keyboard and gamepads

The same view's key listener becomes the session's too. With a keyboard attached, keys reach `onKeyDown` / `onKeyUp` as
DOM `key` / `code` (with modifiers and `repeat`); system keys -- back, home, volume, media -- stay Android's. With a
gamepad attached, it appears in `migo.getGamepads()` on the standard mapping (`mapping: "standard"`, 4 axes, 17 buttons)
and arriving or leaving fires `onGamepadConnected` / `onGamepadDisconnected`; a stick counts only past the device's dead
zone, an analogue trigger with no button signal of its own is pressed past 30/255 of its travel, and a hat switch is the
d-pad. A pad's back key is not given to the game: it is the player's way out of it. Android sends keys and gamepad
motion to the **focused** view: `GameSurfaceView` is focusable and takes focus in `setInputView`, and a view of your own
must be focusable and take focus; when forwarding by hand, use `session.dispatchKeyEvent(ev)`. Pads already connected
when the session is created arrive at once, and all of them leave when it closes.

## State broadcasts: `OnStateChangeListener`

`setOnStateChangeListener(listener)` receives the engine's loading / running / error state transitions — use it to drive the loading UI; **do not** estimate state with `SystemClock`. `GameSessionListener` (a separate interface) provides finer-grained loadingStart/loadingEnd hooks.

## Four methods directly tied to native

| Method | Semantics |
| --- | --- |
| `updateSurface(surface, w, h)` | Called from `surfaceChanged`; w/h are **physical pixels** (Surface buffer dimensions), so pass the original values from the system callback directly |
| `onSurfaceDestroyed()` | Does not destroy the session; marks the Surface invalid and corresponds to the JS `onHide` path |
| `setDebugEnabled(boolean)` | Toggles DebugOverlay at runtime |
| `getPaths()` | Provides `GamePaths.getCodeDir()` and others; the location for `game.js` |

## Handler setters (11 domains + Listener)

Install these before opening the package; see the detailed contract in [Host capabilities overview](/docs/en/capabilities/overview/):

```java
session.setMessageHandler(...);      setAuthHandler(...);
session.setPermissionHandler(...);   setAdHandler(...);
session.setSettingHandler(...);      setShareHandler(...);
session.setNavigationHandler(...);   setPaymentHandler(...);
session.setSubpackageHandler(...);   setGameLogHandler(...);
session.setEcosystemHandler(...);
session.setListener(GameSessionListener);   // loading-level hooks
```

Not setting a handler means the fallback in the overview table applies. After installing one, do not swap it mid-session — in-flight requests already hold the sink for the old handler.

`EcosystemHandler` is the host's own ecosystem (friends and groups, cloud storage, live channels, subscription messages, privacy agreements, ...): requests arrive by content API name at one `call(request, sink)`, the names being the closed set in the contract's `ecosystem.names.calls`. Two things go the other way. `postEcosystemEvent(name, data[, reply])` posts events such as `onVoIPChatStateChanged`; with an `EcosystemReply` (`onCopyUrl` / `onHandoff` / `onNeedPrivacyAuthorization`) content's answers come back, the last with `done=true`, and nothing listening or a runtime restart still ends it with `null`. `setEcosystemValue(name, value)` reports what `getExtConfigSync`, `isChatTool` and the other synchronous getters return; `null` withdraws it.
