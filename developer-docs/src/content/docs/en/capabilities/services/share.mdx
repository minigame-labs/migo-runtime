## Three requests

Every share content starts is a request the host answers, each through its own method:

| migo API | Android `ShareHandler` | C ABI `MIGO_HOST_SERVICE_SHARE` |
| --- | --- | --- |
| `migo.shareAppMessage(options)` | `shareAppMessage(ShareRequest, ShareSink)` | `SHARE_APP_MESSAGE` 0 |
| `migo.shareMessageToFriend(options)` | `shareMessageToFriend(FriendShareRequest, ShareSink)` | `SHARE_MESSAGE_TO_FRIEND` 1 |
| `migo.showShareImageMenu(options)` | `showShareImageMenu(ImageShareRequest, ShareSink)` | `SHOW_SHARE_IMAGE_MENU` 2 |

On Android, register with `GameSession#setShareHandler(ShareHandler)`. A C ABI host declares `MIGO_HOST_SERVICE_SHARE` in
its `host_services` and answers by method number in `on_host_service_call`.

A request is what content passed to the call, as it passed it. The `migo.onShareAppMessage` listeners answer the
menu's "share" item, a different flow, and have no say over an active `shareAppMessage`. An option content did not
set is absent (an empty string on the Android request objects).

## Image paths

Each request names at most one image — `imageUrl` for `shareAppMessage` and `shareMessageToFriend`, `path` for
`showShareImageMenu`. The host receives the **real file path** behind it in the game's sandbox (a file under `/user`,
`/tmp`, `/cache` or in the package; a relative path is resolved against the package root), readable until the request
settles. It is never content's own string, so content cannot have the host read a file outside the sandbox; a path
outside it, or one with no file, fails before the request leaves the engine. Only `shareAppMessage`'s `imageUrl` may
be an http(s) URL, which reaches the host as is; the other two refuse network images.

## Request fields

`ShareRequest` (`SHARE_APP_MESSAGE`):

| Field | Meaning |
| --- | --- |
| `title` | Share title; empty when content set none |
| `imageUrl` | An http(s) URL or a real file path; empty when unset |
| `query` | Query string the launched game receives, such as `a=1&b=2`, without a leading `?` |
| `imageUrlId` | Platform image id; ignore it if the host cannot resolve ids for that platform |
| `toCurrentGroup` | Whether a share made from a group's toolbar goes back to that group; `true` unless content said otherwise |
| `path` | Independent subpackage path; empty when unset |

`FriendShareRequest` (`SHARE_MESSAGE_TO_FRIEND`):

| Field | Meaning |
| --- | --- |
| `openId` | The friend's openId, as content supplied it; never empty |
| `title` / `imageUrl` / `imageUrlId` | As above; `imageUrl` is only ever a real file path |
| `query` | The query `migo.setMessageToFriendQuery()` set, which the friend's enter options carry as `query.query` |
| `shareMessageToFriendScene` | Likewise `query.shareMessageToFriendScene`, 0–50; `null` when unset (absent on the C ABI) |

`ImageShareRequest` (`SHOW_SHARE_IMAGE_MENU`):

| Field | Meaning |
| --- | --- |
| `path` | A real file path; never empty |
| `needShowEntrance` | Whether the image's message carries an entry into the game |
| `entrancePath` | Where that entry opens the game; empty for its default |

## Answering

Settle each request exactly once through its `ShareSink` (on the C ABI, `migo_session_complete_host_service_call`):

| Method | Meaning |
| --- | --- |
| `settleShared()` | The share flow finished; it does not mean the user actually sent a message |
| `fail(int errCode, String errMsg)` | Failure; `errMsg` is passed to content verbatim |

A share waits on the player for as long as they take; the runtime sets no deadline. Calls arrive on the runtime's host
thread, so do not block in them; `ShareSink` may be called from any thread, and the first settle wins.

When a `shareMessageToFriend` ends, content's `migo.onShareMessageToFriend` listeners receive `{success, errMsg}` —
derived from that request's settlement; the host posts no event of its own.

## The share menu

The menu ("share", "share to moments", "add to favorites") is the host's. A mini game's share items start hidden, and
content turns them on with `showShareMenu`:

- After every `showShareMenu` / `hideShareMenu` / `updateShareMenu` the host receives the menu's **whole state** —
  Android `ShareHandler.onShareMenuChanged(ShareMenu)`, C ABI command `SET_SHARE_MENU` 3 (`{"menus", "withShareTicket",
  ...the updateShareMenu fields}`). "Share to moments" is only ever offered beside "share".
- When the player picks an item, the host asks the game what to share — Android
  `GameSession.requestMenuShare(menu, MenuShareCallback)`, C ABI event `EVENT_MENU_SHARE` 0 (`{"menu", "replyId"}`, `menu`
  being `shareAppMessage`, `shareTimeline` or `addToFavorites`).
- Content's `onShareAppMessage` / `onShareTimeline` / `onAddToFavorites` listener answers (the last one that returns an
  object decides; a `promise` in an `onShareAppMessage` answer is waited on for up to three seconds and its result
  decides), exactly once — `MenuShareCallback.onShareContent(MenuShareContent)`, C ABI command `MENU_SHARE_REPLY` 4
  (`{"replyId", "menu", "content"}`). With nothing listening, or when the runtime restarts first, the answer is `null`
  and the host shares its own defaults (the game's name, its icon). An image in the answer is again a real file
  resolved through the sandbox (readable for the session) or an http(s) URL; an image that is not the game's own file
  is dropped.

## Without a host

With no handler (or a C ABI host that did not declare the share service), all three fail with
`<api>:fail not supported` and code `-2`. They settle rather than stay silent: content commonly awaits a share before
resuming, so a dropped request is a paused game.

A `migo.shareAppMessage()` success only means the share flow finished; as on common mini-game platforms, content is not
told whether the user really sent a message, and rewarding on it has no factual basis.
